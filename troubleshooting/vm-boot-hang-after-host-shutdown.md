# 宿主机强制关机后，实验虚拟机开机卡住

> 已脱敏：不含真实主机名、IP、拓扑、设备配置、账号、内部系统名。

- 时间：2026-11（前一晚至当天上午）
- 类型：系统（虚拟化环境）
- 影响：一台实验虚拟机开机后卡住，重启两次无效，之后改用正常关机恢复。只影响实验环境，未涉及生产系统。

## 原理：为什么强制断电会留下问题

| 关机方式 | 客户机是否收到关机信号 | 是否正常卸载文件系统、刷盘 | 对下次启动的影响 |
|---|---|---|---|
| 宿主机直接关机（本次发生） | 否，虚拟机被突然停止 | 否，内存里未写完的数据可能没有落盘 | 可能留下不一致的状态，下次启动可能卡住 |
| VirtualBox 电源关闭（相当于拔电源） | 否 | 否 | 同上 |
| VirtualBox 关机（ACPI，Advanced Configuration and Power Interface，高级配置与电源接口；本次恢复时使用） | 是，系统收到关机请求后自己关机 | 是，systemd 依次停止服务、卸载文件系统 | 状态干净，正常启动 |
| 系统内执行 `shutdown` / `systemctl poweroff` | 不适用，由系统自己发起 | 是 | 同上 |

日志文件系统（journaling filesystem）用日志保证元数据（目录、inode 等结构）一致，但不保证所有正在写入的文件内容完整。所以断电后，下次挂载时可能要回放日志或做检查。只要某一步出错、等待输入或超时，启动就会停在那里。systemd 的常见行为（一般知识）：某个挂载失败且 `/etc/fstab` 没有写 `nofail` 时，等待超时后会进入紧急模式（emergency mode），等待输入。

## 现象

- 11-07 上午，其中一台客户端虚拟机开机后卡住，画面停在同一处，不再前进。用户 08:20 左右报告。

## 排查过程

1. 第一次重启：在 VirtualBox 里操作（用户记得做了"关闭"，具体选的哪一项未确认），重新开机后仍停在同一处，没有进入系统。
2. 第二次重启：仍然卡在同一处。
3. 怀疑磁盘：用户认为这台虚拟机只有两块原始虚拟盘，且没有做过 RAID 等改动，不可能掉盘。助手当时提出"磁盘缺失"的假设。两者都没有取证确认。
4. 怀疑 CPU 忙循环：助手当时提出，未取证确认。
5. 怀疑强制断电导致文件系统损坏：用户提出，未检查。
6. 有效操作：在 VirtualBox 控制菜单选"关机"（ACPI）。控制台打印了一串关机日志，随后虚拟机自动启动，系统恢复正常，之后没有再卡住。用户没有手动启动。
   - 用户两次描述略有不同：一次说"它就自动重启了"，一次说"输出一系列控制台日志，接着自动启动成功"。自动启动的原因未查清。
7. 恢复后，客户端的网络和服务实验正常，见同日的 A4 笔记（`labs/2026-11-07-troubleshoot-service-network.md`）。

- 可以沉淀成检查项的：
  - 下班前在虚拟机内正常关机，不直接关宿主机。
  - 启动卡住时的取证清单（未执行，待下次实际使用时验证）：`journalctl -b -1`（上一次启动的日志）、`journalctl -b -p err`、`systemctl --failed`、`dmesg -T | grep -i -E 'fsck|error'`、检查 `/etc/fstab` 中非根盘的挂载项是否写了 `nofail`。
